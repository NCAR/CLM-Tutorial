Hybrid, Branch, and Startup#

CLM can be initialized in one of three ways: startup, hybrid and branch. These are set with the variable $RUN_TYPE in env_run.xml.

1. Understanding the three run types#

Startup#

In a startup run (the default), CLM is initialized from the basic default initial conditions. The coupler does not need an initial file.

Hybrid#

A hybrid run indicates that CLM is initialized using initialization datasets from a previous case.

A hybrid run allows users to bring together combinations of initial/restart files from a previous case (specified by $RUN_REFCASE) at a given model output date (specified by $RUN_REFDATE). The model start date for the hybrid run (specified by $RUN_STARTDATE) can be modified relative to the reference case.

In a hybrid run, the model does not necessarily continue in a bit-for-bit fashion with respect to the reference case, though this depends on your component set. For land-only cases (e.g., “I” cases), a hybrid should be bit-for-bit, as long as the code and no other settings change. However, in coupled configurations (e.g., if CLM is coupled to the atmosphere), this will not be the case.

Branch#

This is somewhat analogous to a hybrid run with more restrictive restart constraints.

In a branch run, CLM is initialized using a consistent set of restart files from a previous run (determined by the $RUN_REFCASE, $RUN_REFDATE, and $DRV_RESTART_POINTER variables in env_run.xml).

In a branch run, setting $RUN_STARTDATE is ignored because CLM obtains the start date from its restart datasets. Therefore, the start date cannot be changed for a branch run. This is the same mechanism that is used for performing a restart run (where $CONTINUE_RUN is set to TRUE in the env_run.xml file).

The case name is generally changed for a branch run, although it does not have to be.

Branch runs are typically used in coupled configurations when sensitivity or parameter studies are required, or when settings for history file output streams need to be modified while still maintaining bit-for-bit reproducibility.

It is important to remember that the $RUN_TYPE variable is only relevant when a run is initialized. Let’s again take a look at the exercises we did in the chapter Changing run length:

Evaluate your understanding

Assume our configuration of CLM simulates 50 model years per wallclock day on Derecho. The maximum wallclock request is 12 hours. If you want to run the model for 100 years, what values should be set for STOP_OPTION, STOP_N and RESUBMIT?

We worked out that for a total of 100 years, we will need 4 submissions. We can set:

STOP_OPTION = 'nyears', STOP_N = 25, RESUBMIT = 3

Now, if you want this run to be a hybrid run, what variables should you modify, and at which stage?

Hint!

The $RUN_TYPE variable is only important at the initial run when CONTINUE_RUN is set to FALSE.

Click here for the solution

Set RUN_TYPE='hybrid' in env_run.xml before submitting the initial run.

Bonus question:

What happens if you set run_type='branch' after the 2nd resubmission when the CONTINUE_RUN=TRUE?

Answer: Nothing changes, because RUN_TYPE is only relevant for an initial run when CONTINUE_RUN is set to FALSE!

Evaluate your understanding

In the exercise above, if you have set RUN_TYPE='hybrid' and RESUBMIT=3 before the initial run, what are the values of CONTINUE_RUN, RESUBMIT, and RUN_TYPE at the time of:

  • the initial submission of 25 years

  • the next submission of 25 years

  • the 3rd run (2nd resubmission) of 25 years?

Click here for the solution

  • the initial submission of 25 years:

     CONTINUE_RUN=FALSE, RESUBMIT=3, RUN_TYPE='hybrid'

    because when the run is first initialized, CONTINUE_RUN=FALSE

  • the next submission of 25 years:

    CONTINUE_RUN=TRUE, RESUBMIT=2, RUN_TYPE='hybrid'

    because RESUBMIT>0, CONTINUE_RUN will automatically switch to TRUE after the initial run, but RUN_TYPE won’t change.

  • the 3rd run (2nd resubmission) of 25 years:

    CONTINUE_RUN=TRUE, RESUBMIT=1, RUN_TYPE='hybrid'

    CONTINUE_RUN stays TRUE, RESUBMIT decreases by 1, RUN_TYPE won’t change.

2. When to use branch vs. hybrid?#

Branch and hybrid runs are useful if you have an experiment which only slightly differs from your control, but you want to make a slight modification, add history output, or start your simulation from a CESM spun-up initial state and maintain an exact restart (which mimics what the model would do if it had kept running in the original setup).

Use a hybrid run: for most applications where you do NOT need bit for bit restart. You CAN specify a new start date for your model run.

Use a branch run: only for coupled model applications which require exact restart. It is typically used when sensitivity or parameter studies are required, or when settings for history file output streams need to be modified while still maintaining bit-for-bit reproducibility. You CANNOT specify a new start date for your model run. It will be assigned by the reference case ($RUN_REFDATE).

3. Restart files for branch and hybrid runs#

For runs that are initialized as hybrid or branch runs, we will need restart/initial files from previous model runs (as specified by the variables, $RUN_REFCASE, $RUN_REFDATE, and $DRV_RESTART_POINTER). See the Chapter Run variables related to run type for details.
